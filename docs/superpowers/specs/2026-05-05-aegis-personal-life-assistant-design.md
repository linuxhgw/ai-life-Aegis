## 一、核心定位

**Hermes是大脑，我们只做两件事：入口和出口。**

```
┌─────────────────────────────────────────────────────────────┐
│                         入口层（我们开发）                    │
│     Webhook   桌面客户端   语音   Android（后续）              │
└──────────────────────────┬──────────────────────────────────┘
                           │ 指令 / 事件
┌──────────────────────────▼──────────────────────────────────┐
│                 大脑层（复用 → 魔改 → 自研）                  │
│   理解意图   ·   记忆历史   ·   决策   ·   生成技能           │
│   Phase 1-2：直接复用    Phase 3-4：浅层魔改   Phase 5+：自研 │
└──────────────────────────┬──────────────────────────────────┘
                           │ 决策 / 指令
┌──────────────────────────▼──────────────────────────────────┐
│                         出口层（我们开发）                    │
│     UI类：弹窗   遮罩   锁屏   通知   桌宠表情                 │
│     计划类：待办清单   系统建议   定时任务                     │
│     系统类：Webhook   写文件                               │
└─────────────────────────────────────────────────────────────┘
```

## 二、产品阶段路线图

### Phase 1：功能闭环（6-8周）

**一句话目标：目标拆解 + 今日计划 + 五级提醒 + 计划调整多层拦截，跑通完整闭环。**

这个阶段**不开发桌宠UI，不开发Android端，不碰Hermes内部**。

Phase 1有两个核心能力：

1. **正向闭环**：自然语言设定目标 → Hermes拆解 → 今日计划 → 五级提醒 → 执行记录
2. **计划调整闭环**：计划变更请求 → 多层拦截追问 → 验证通过 → 计划更新 + 通知调整

**核心功能2：任务反馈 + 双线升级提醒**

每个拆解出来的任务，需要用户交付具体的**成果证明**，而不是简单的"点确认"。

任务反馈类型：

| 反馈类型 | 说明 | 适用场景 |
|----------|------|----------|
| 文字输入 | 用户输入一段文字 | 记录心情、写下感想 |
| 拍照上传 | 用户拍照作为证明 | 饮食记录、运动打卡 |
| 打卡确认 | 一键确认完成 | 简单任务快速确认 |
| 位置确认 | 获取当前位置 | 确认是否到达某地 |
| 多选确认 | 从预设选项中选择 | 今日饮食/运动完成情况 |

提醒升级有**两条独立的升级通道**，每1分钟升级一次：

**通道1：反馈方式升级（逼用户提交更多证明）**

```
第1次提醒（L1）→ 要求：文字输入（"今天吃了什么？"）
    ↓ 无反馈，1分钟后
第2次提醒（L2）→ 要求：拍照上传（"请拍照记录"）
    ↓ 无反馈，1分钟后
第3次提醒（L3）→ 要求：位置确认（"你在哪里？"）
    ↓ 无反馈，1分钟后
第4次提醒（L4）→ 要求：拍照+文字（更具体描述）
    ↓ 无反馈，1分钟后
第5次提醒（L5）→ 升级到通知强度，继续要求反馈
```

**通道2：通知强度升级（逼用户注意这条消息）**

```
第1次（L1）：微信消息 + Windows通知中心通知，同时推送
    ↓ 无响应，1分钟后
第2次（L2）：微信@提醒 + 弹窗弹出
    ↓ 无响应，1分钟后
第3次（L3）：弹窗置顶 + 提示音
    ↓ 无响应，1分钟后
第4次（L4）：倒计时遮罩（30秒），遮罩期间要求输入反馈
    ↓ 无响应，1分钟后
第5次（L5）：全屏阻断，需提交反馈才能解除
```

**两条通道同时运行，互不冲突：**
- 反馈方式通道：逼用户提供更具体的证明
- 通知强度通道：逼用户注意这条消息
- 两者可以组合（如：第3次提醒 = 要求拍照 + 弹窗置顶 + 提示音）

**升级示例**：

任务：今晚8点记录饮食

```
20:00
  → 通道1：要求文字输入
  → 通道2：微信+通知中心同时推送

20:01（无反馈）
  → 通道1：要求拍照上传
  → 通道2：微信@提醒 + 弹窗弹出

20:02（无反馈）
  → 通道1：要求位置确认
  → 通道2：弹窗置顶 + 提示音

20:03（无反馈）
  → 通道1：要求拍照+文字
  → 通道2：30秒倒计时遮罩

20:04（仍无反馈）
  → 通道2：全屏阻断
  → 通道1：必须提交拍照+文字才能解除阻断
```

**阶段一验收条件中对应调整：**
- L1-L5的升级是**通知强度**的5个等级
- 反馈方式升级独立于通知强度，共4级升级（文字→拍照→位置→拍照+文字）
- 两条升级通道的组合构成完整的提醒升级策略

**核心功能3：计划调整多层拦截（Phase 1关键差异化）**

这是Aegis的核心差异化：**系统不是被动接受变更，而是主动追问验证后才放行。**

典型场景：用户说"今晚计划要调整"

```
用户：今晚计划要调整，老婆约了约会
    ↓
Hermes 第1层拦截：理解意图
    ↓
"明白，你想调整今晚的计划。
    是想完全取消今晚的减肥任务，
    还是推迟到其他时间？"
    ↓
用户：推迟到明天
    ↓
Hermes 第2层拦截：影响评估
    ↓
"推迟一天看似影响不大，
    但根据你过去的数据，
    一旦'推迟'，连续坚持的概率会下降60%。
    你确定要推迟，而不是今晚只做一半？"
    ↓
用户：确定要推迟，老婆约会不能拒绝
    ↓
Hermes 第3层拦截：条件交换
    ↓
"理解，约会确实重要。
    建议调整为：今晚执行'��录饮食'任务
    （只需要拍照发给我，2分钟），
    '不吃零食'任务推迟到明天。
    这样至少保持一个习惯不断档。"
    ↓
用户：行，就这样
    ↓
Hermes 放行
    │
    ├── 今日计划更新：任务调整
    ├── 提醒更新：新增20:00「记录饮食」提醒（L1）
    ├── 明日计划更新：「不吃零食」任务加入明天
    └── 记录原因：「老婆约会，不可推迟」
```

**多层拦截的拦截逻辑：**

| 层级 | 拦截目标 | 典型问题 |
|------|----------|----------|
| L1 | 理解真实意图 | "是想取消还是推迟？还是有其他安排？" |
| L2 | 评估影响 | "推迟会导致连续打卡中断，确定吗？" |
| L3 | 提出替代方案 | "能不能只做一部分，或者换个时间？" |
| L4 | 确认最终决心 | "好的，今晚任务已调整，明天的已排好。" |

拦截层级数取决于变更的"代价"：
- 轻微调整（改时间）：1-2层
- 中度调整（推迟一天）：2-3层
- 重大变更（取消目标）：3-4层

**Phase 1验收条件：**
- 用户在微信输入"我要减肥" → 收到完整的目标拆解
- 今日计划正确生成，包含多个可执行的今日任务
- **L1-L5全部5个等级提醒都能正确触发**
- 提醒升级策略正确（L1→L2→L3→L4→L5）
- 用户说"今晚计划要调整" → 进入多层拦截流程
- 多层拦截追问后 → 计划更新 + 提醒重新排期
- 提醒结果（完成/跳过/拖延）被记录
- 第二天可以继续对话："昨天减肥计划执行得怎么样"

**Phase 1不包含：**
- ❌ 桌宠UI（Phase 2）
- ❌ Profile系统（Phase 2）
- ❌ Android端（Phase 3）
- ❌ 大脑魔改（Phase 4）

### Phase 3：Android端（4-6周）

**Android作为移动端入口和执行器，PC端专注显示和配置。**

**Android核心功能：**

- 悬浮球（常驻，单击展开状态卡）
- 移动端提醒接收（弹窗、遮罩、通知）
- 移动端Perception（感知当前App、WiFi）
- 移动端Profile同步（与PC共用同一Profile状态）

```
┌─ 悬浮球 ─────────┐        ┌─ 状态卡（单击）────────┐
│                  │        │ 🛡️ 工作日专注           │
│    🛡️            │   →    │ WiFi：公司              │
│                  │        │ 今日：5次/80%           │
│                  │        │ ───────────────────     │
│                  │        │ [⏸ 暂停] [🔄 切换]      │
└──────────────────┘        └────────────────────────┘
```

**跨设备协同：**
- PC开启专注模式 → Android自动同步Profile
- Android上触发提醒 → PC桌宠同步显示状态
- 两端共用同一Profile状态，通过局域网WebSocket同步

**Phase 3验收条件：**
- [ ] Android悬浮球正确显示当前Profile和状态
- [ ] PC切换Profile后Android自动同步
- [ ] Android端的提醒（遮罩/通知）正确弹出
- [ ] Android感知（App/WiFi）正确上报

### Phase 4：大脑层深化（持续迭代）

**在前三个阶段积累了对Hermes足够理解后，开始浅层魔改，必要时自研替代。**

**浅层魔改方向：**

| 方向 | 具体内容 |
|------|----------|
| System Prompt定制 | 调整Hermes的决策风格、响应格式 |
| 记忆Schema定制 | 干预记录、服从率、逃避模式的自定义存储格式 |
| 自研规则引擎 | 补充Hermes的ReAct决策，加入更确定性的规则匹配 |
| 自研Profile状态机 | Profile切换、冲突检测、免疫期逻辑 |
| 自研习惯学习 | 规则统计、Profile切换预测、升级建议 |

**深度自研的触发条件：**
- 当Hermes的记忆系统无法高效支持"干预服从率"这类垂直指标查询时
- 当ReAct决策的延迟无法满足实时干预需求时
- 当需要更精细的Profile状态机逻辑时

## 三、Phase 1详细设计：功能闭环

Phase 1是整个项目的地基，核心目标是跑通"目标→拆解→计划→提醒→记录"完整闭环。

### 3.1 典型用户对话流程

**对话示例1：设定目标**

```
用户：我要减肥
Hermes：
  好的！我来帮你拆解一下减肥目标。

  【长期目标】6个月内减重10kg
  【短期目标】本月：饮食控制 + 每周运动3次

  【今日任务】
  ☐ 07:30 晨起称重（要求：拍照上传体重秤读数）
  ☐ 12:00 午餐记录（要求：拍照上传午餐）
  ☐ 19:00 今晚饮食计划提醒（要求：文字确认）
  ☐ 20:00 饮食打卡（要求：拍照上传晚餐）
  ☐ 22:00 睡前检查（要求：文字总结今日）

  每条任务都有对应的完成证明要求。
  提醒会逐步升级：1分钟不响应就升级。
  [全部确认]  [修改]  [重新拆解]
```

**对话示例2：提醒执行（双线升级）**

```

  通道1：要求拍照上传

20:01（无反馈）

  通道2：升级为微信@提醒 + 弹窗

20:02（仍无反馈）
  通道1：升级为拍照+文字说明
  通道2：升级为弹窗置顶 + 提示音
  → Hermes调用show_popup置顶 + play_sound("alert")

20:03（仍无反馈）
  通道1：维持拍照+文字
  通道2：升级为30秒倒计时遮罩
  → Hermes调用show_countdown_overlay("请提交饮食记录", 30)

20:04（仍无反馈）
  通道2：升级为全屏阻断
```

### 3.2 目标拆解逻辑（Hermes行为模式）

```
输入："我要减肥"
    ↓
Step 1：理解目标
  提取：目标类型（健康）、方向（减肥）、时间范围（长期）
    ↓
Step 2：查询历史
  记忆中有无相同/相关目标？
  → 有：调取上次计划，询问"继续上次的目标吗？"
  → 无：新建
    ↓
Step 3：拆解目标
  长期（6个月）：具体体重/体脂目标
  短期（1个月）：阶段里程碑
  本周：具体可执行任务
  今日：精确到时间点的待办
    ↓
Step 4：确定提醒时机
  根据目标类型和用户历史，确定提醒时间点
  减肥场景：饭前提醒 > 饭后检查 > 睡前升级
    ↓
Step 5：确定提醒方式
  饭前提醒 → 微信消息（轻量）
  饭后检查 → 弹窗+通知（中等强度）
  睡前升级 → 倒计时遮罩（强制）
    ↓
Step 6：输出计划，等待确认
```

### 3.3 提醒执行器（出口层核心）

提醒执行器接收Hermes的指令，驱动双线升级提醒：

```
提醒任务：{
  task_id: "...",
  message: "今晚饮食打卡",
  scheduled_time: "20:00",
  required_feedback: "photo",        // 要求的反馈类型
  escalation_interval_seconds: 60     // 每60秒升级一次
}
    ↓
scheduled_time到达
    ↓
双线同时启动：
    │
    ├── 通道1（反馈升级）：
    │   L1: 要求文字输入
    │   L2: 要求拍照上传
    │   L3: 要求位置确认
    │   L4: 要求拍照+文字
    │   L5: 维持L4要求，等待提交
    │
    └── 通道2（通知升级）：
        L1: 微信消息 + 通知中心
        L2: 微信@提醒 + 弹窗
        L3: 弹窗置顶 + 提示音
        L4: 30秒倒计时遮罩
        L5: 全屏阻断（必须提交反馈解除）
    │
    ↓
每60秒若未收到反馈：
    → 反馈通道升级一级
    → 通知通道升级一级
    ↓
收到有效反馈 → 任务完成，记录到记忆
收到无效反馈 → 要求重新提交
全屏阻断解除 → 任务完成（即使质量一般）
```

### 3.4 Phase 1 MCP工具清单

**Perception工具（最小集）：**

```json
get_current_time()
  → { time: string, weekday: int, date: string }

get_system_state()
  → { pc_online: bool, screen_on: bool }
```

**Intervention工具（L1-L5全部Phase 1实现）：**

```json
// ===== 通知/提醒类 =====

// L1：微信消息（Hermes插件或自研接口）
send_wechat_message(message: string)
  → { sent: bool, error?: string }

// L1-L2：系统通知
show_notification(title: string, body: string)
  → { shown: bool }

// L2-L3：弹窗
show_popup(title: string, message: string, buttons?: string[])
  → { clicked: string, timeout: bool }

// L2-L3：提示音
play_sound(sound_type: "gentle" | "alert" | "alarm")
  → { played: bool }

// ===== 用户反馈收集类 =====

// 文本输入（收集理由/文字反馈）
get_text_input(prompt: string)
  → { submitted: bool, text: string }

// 拍照上传（收集图片证明）
get_photo_input(prompt: string)
  → { submitted: bool, photo_base64: string }

// 位置确认（收集当前位置）
get_location_input(prompt: string)
  → { submitted: bool, latitude: number, longitude: number, address: string }

// 多选确认（从预设选项中选择）
get_choice_input(prompt: string, options: string[])
  → { submitted: bool, choice: string }

// ===== 强制类 =====

// L4：倒计时遮罩（可附带要求反馈类型）
show_countdown_overlay(message: string, seconds: number, required_feedback?: string)
  → { completed: bool, waited_seconds: number, feedback_submitted?: string }

// L5：全屏阻断（必须提交反馈才能解除）
show_fullscreen_block(message: string, required_feedback: string)
  → { completed: bool, feedback_submitted: string }

// L5：屏幕锁定
lock_screen(duration_seconds: number)
  → { unlocked: bool }
```

**Phase 1 L5技术说明：**

- `show_fullscreen_block`：使用Windows API创建无边框全屏窗口，禁用Alt+Tab，不可最小化，**必须提交反馈才能解除**
- `lock_screen`：调用Windows锁屏API（`LockWorkStation`），配合遮罩防止立即解锁

## 五、Phase 2 详细设计：多入口 + Profile

### 5.1 Windows桌宠客户端（Phase 2新增）

**定位**：Phase 2的入口层，承载对话+快捷按钮+Profile管理。

**对话区**：和微信体验一致，打字发送给Hermes，收到回复。

**快捷按钮区**：预设动作，一键触发，不需要打字。

预设按钮（用户可配置）：
- 专注模式（激活工作日专注Profile）
- 假期模式（激活假期Profile）
- 暂停监控（临时停止干预）
- 查看计划（打开计划中心）
- 定时（设置定时任务）

**状态栏**：始终显示当前Profile、运行状态、今日统计。

### 5.2 Profile系统（Phase 2新增）

Profile = 一套"激活条件 + 规则 + 提醒方式"的组合。

**Profile编辑器**：

```
基本信息
  名称：[工作日专注__________]
  图标：[⚡▼]

激活条件（满足任一即激活）
  [x] 定时  周一至周五 [09:00 ──●──── 18:00]
  [x] WiFi  [Office-5G▼]（可选）

提醒方式
  [x] 微信消息
  [x] 桌面弹窗
  [x] 提示音
  组合：[微信+弹窗+提示音 ▼]

冲突处理
  多个Profile同时激活时：
  ○ 取最高level
  ● 提示我选择
  ○ 优先级高者覆盖
```

**Profile → Hermes Skill自动转换**：

用户在UI配置Profile → 系统生成Hermes Skill YAML → Hermes加载 → 定时/条件触发时自动执行。

```yaml
# auto-generated: 工作日专注
name: 工作日专注
triggers:
  - type: time
    cron: "0 9 * * 1-5"
  - type: wifi
    ssid: "Office-5G"
conditions:
  active_hours:
    start: "09:00"
    end: "18:00"
    days: [1,2,3,4,5]
actions:
  - activate_profile: 工作日专注
  - set_reminder_channels: ["wechat", "popup", "sound"]
```

### 5.3 计划中心（Phase 2新增）

计划中心是所有"计划类"内容的统一入口，承载三类：

**今日待办**：
- 来自目标拆解的每日任务
- 来自Profile定时激活的任务
- 用户手动添加的任务

**定时任务**：
- Profile定时切换
- 定时提醒
- 周期性目标检查

**系统建议**：
- 基于历史数据的规则优化建议
- Profile切换建议
- 目标进度评估
